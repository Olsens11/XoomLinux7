# MZ600 BCM4329: selected OEM-to-Linux7 compatibility design (2026-10-29)

**Decision status: source-backed design selected; implementation / physical acceptance OPEN.** This is not a new patch, kernel installation, upstream submission, regulatory certification, or a claim of working normal 5 GHz operation. Preserve the installed, physically functional original nine-patch Debian p10 system. Owner mandate: implement the smallest proven existing interface preserving Motorola/Broadcom firmware functions and standard Linux wireless semantics, one logical issue per patch.

> **2026-10-29 PHYSICAL UPDATE — hypothesis resolved:** The [one-use read-only country-iovar test](../checkpoints/MZ600_COUNTRY_IOVAR_US_REV0_PHYSICAL_ROLLBACK_PASS_2026-10-29.md) on the original connected generic firmware directly returned **`err=0 abbrev=US ccode=US regrev=0`** (not the OEM factory `US/69`). Lab core was loaded only from RAM, then removed; original firmware/NVRAM/core/WCC SHA and Wi-Fi restored, independent postflight PASS, COM9 released. **The country-abbrev short-circuit is now a measured live issue: an `US-US-69` DT map by itself will not correct existing initial `US/0`.** Restore/test authentic model-appropriate OEM NVRAM defaults and firmware support first; dynamic DT mapping is still the established country-change interface. This difference is not proof that US/0 violates regulatory limits or that setting US/69 will enable 5 GHz. No country changes were made.

## What we selected, and why

**Solution:** use the real per-board OEM firmware/NVRAM/default limits, **stock** Linux `brcmfmac` and `cfg80211` regulatory mechanisms, and two *existing* Broadcom-facing interfaces for the incompatible legacy edges:

1. **Country / calibration boundary (BOARD/DT scope, *not WIFI-01*):** Board-specific `brcm,ccode-map` strings translate ISO country hints from Linux to firmware locale/revision. The existing `brcmf_cfg80211_reg_notifier` reads firmware country, translates it through `brcmf_translate_country_code`, sends firmware `country` only when appropriate, then refreshes `brcmf_setup_wiphybands` on success. This was explicitly added to upstream `brcmfmac` in an Arend van Spriel-reviewed 2021 series to support RF/board-specific country revisions. **No generic driver change is justified for country translation.** The map belongs only to the actual Stingray/MZ600 model and RF/firmware variant after verification, not all Xooms using a shared DTS.
2. **Legacy channel inventory boundary (WIFI-01 only):** keep the modern `chanspecs` branch fully unchanged on supported chips/firmware. On BCM4329 firmware that cannot provide `chanspecs`, the proven legacy `BRCMF_C_GET_VALID_CHANNELS` provides a *currently valid* channel list. Validate count and values against actual 2.4/5 GHz band templates, maintain 20-MHz-only capability if that is the true firmware limit, and don't invent hardware channels. Querying the same firmware's `per_chan_info` returned native `BCME_UNSUPPORTED=-23` for **all six actually tested encodings**, so no radar/passive metadata may be synthesized from its failures.
3. **Policy boundary:** remain governed by *both* firmware/board limitations and the current Linux `cfg80211` domain / signed `wireless-regdb` restrictions. A valid channel is not an authorization to transmit; unknown firmware-specific radar/passive metadata cannot be treated as `no restriction`. The previous broad 5 GHz `NO_IR` was a conservative lab safeguard, **not a proven production-equivalent Motorola policy**, and cannot become a permanent cross-country workaround simply because it hides uncertainty. Until metadata/regulatory equivalence is established, keep conservative safety and avoid claiming production support. Preserve legitimate country changes and cfg80211's own dynamic regulatory flags.

## Two implementation traps we must explicitly test

**A. Country already matches, revision does not.** The pinned `brcmf_translate_country_code()` returns `-EAGAIN` when requested ISO country equals firmware `country_abbrev` **before** examining `settings->country_codes` and revision. A DT mapping alone therefore **cannot repair an incorrect factory-initialized country revision for the already-selected country**. Provide/restore model-appropriate OEM board calibration and verify the firmware's actual country/rev at boot. Only if a measured mismatch remains should we consider the smallest driver change; do not casually change the shared notifier or claim a map alone guarantees rev69. The subsequent COM9 read-only trial **measured US/0**, with an independently verified clean original-Wi-Fi rollback; see the Oct29 checkpoint above. What the original 2012 firmware would report with restored OEM NVRAM remains untested.

**B. Live firmware channel set is not immutable hardware support.** `cfg80211` saves `orig_flags` at registration and recalculates restrictions on regulatory changes; `brcmfmac` populates channels **after** registration and refreshes them after successful country writes. `WLC_GET_VALID_CHANNELS` can be scoped to the current firmware country. Do not permanently store its exclusions as original hardware restrictions, permanently suppress dynamic no-initiation-of-radiation state, clear Linux country restrictions, or assume every regulatory notifier succeeds.

The existing unsigned **WIFI-01 r3 is NOT accepted unchanged**: it treats `-EBADE` as if it meant only unsupported despite pinned `fwil.c` collapsing *many* native firmware errors to `-EBADE`; it inserts broad `NO_IR` when metadata is missing; and its legacy post-registration channel update must be audited for country-change transitions. Retain its measured bounded legacy-list idea, but refine **this same logical patch** only after tests. Do not add a fifth chronological workaround. WIFI-02/03/04 remain separate and unaffected.

## Minimum non-destructive qualification sequence

1. **Source / model tests (completed):** [14-gate pinned-source checker](../../tools/forensics/check_bcm4329_country_boundary_20261029.py) run on the original nine+r3 Linux7 source tree, PASS 14/14; repository validation PASS. This verifies documented source *presence/order*, **not RF behavior**.
2. **Offline board-variant candidate:** prepare DTS mapping of *verified* ISO→firmware/revision entries only, anchored to exact MZ600 US board/firmware variant, and separately model a country update to another known OEM mapping. Do not insert one US mapping into the universal `tegra20-motorola-stingray.dts` because it has generic `motorola,stingray` / `motorola,xoom` compatible values; no new `brcmfmac` country-code machinery. Distinguish exact Motorola table, subset proven for a particular firmware, and no universal XY wildcard assumption (the existing DT property encodes a two-letter ISO code).
3. **Read-only hardware truth:** restore stable exclusive Surface COM9, confirm exact original SHA/connected wlan and no overlay. With an independently guarded single-use RAM module replacement, query **current** firmware `country` iovar for abbreviation/ccode/rev; independently restore original module and NM/WPA. Do not run a country-set experiment just to diagnose the value. The first COM9 trial stopped before staging, but the **subsequent authorized one-use readback completed**: lab module briefly RAM loaded, country read `US/0`, original drivers and Wi-Fi restored, independent postflight PASS. This diagnostic module was *not* persistently installed and the one-use marker is consumed. Next is source-first OEM calibration/firmware compatibility, then a separately gated future test if needed.
4. **OEM candidate check:** compare historical Motorola OEM firmware and factory NVRAM to generic running set; verify matching calibration, exact firmware build and accepted country readback in a sandboxed RAM-only rollback test. Do not publish actual board identities, copied real MAC or proprietary firmware. Verify 2.4 + 5GHz bandlist and bounded channels *after* firmware initialization, before RF scan.
5. **Regulatory-state transitions:** using offline fixtures first, then country-hint observations permitted by local regulations, prove appropriate country/rev translation and channel refresh without permanent lockout. Verify signed regulatory database acceptance, DFS/passive requirements, power limits, scan behavior, association/connectivity and regressions for already-supported 2.4GHz and other chip paths. Avoid an unauthorized live country change or active scan on unqualified frequencies.
6. **Patch acceptance:** revise the existing WIFI-01 in an isolated worktree; apply original nine-member review ordering, strict checkpatch, module CRCs, full zImage/modules/DTB build; follow with consented guarded physical regression + independent postflight. DCO and submission belong to the human owner.

## Rejected alternative designs

- **Universal US/69 or ISO→ISO rev0 hardcode:** rejects legitimate mobility and ignores a documented upstream regression.
- **Synthetic `per_chan_info`/radar flags or a new PHY calibration subsystem:** fabricates data the firmware does not provide; duplicates on-chip logic.
- **Copy the historical broad `alpha2=99` permissive table as the authority:** defeats the distinction between current Linux restrictions and firmware channel inventory.
- **Treat firmware's currently valid 35-channel list as immutable factory capability:** could prevent later lawful country-state changes.
- **Change all `fwil.c` error handling or add global protocol state:** excessive, coupled risk; use native error provenance or a tested narrow fallback.
- **Replace OEM firmware/calibration with guessed 'newer is better' file:** unnecessary compatibility variable, not a demonstrated fix.

**Selected mechanism is now sufficiently grounded to direct engineering. It is not yet physically demonstrated as a complete replacement for r3.** In particular the original country iovar and the regulatory semantics of metadata-absent 5 GHz remain open.
