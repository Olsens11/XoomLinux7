## Required external precedent comparison before choosing a fix (2026-10-29 clarification)

**Owner standing implementation rule:** Preserve the intent and full supported functionality of legacy behavior whose original execution mechanism no longer works; replace only that mechanism with the **smallest source-backed change**. Before changing a patch, investigate **both** upstream Linux/core API practices and the same OEM/driver lineage plus analogous vendor/driver solutions; seek working published code, kernel-doc contracts, maintainers' reviews, and historical regressions. Record exact citations, the behavioral contract, what the precedent did **not** establish, its applicability to the current hardware/firmware, and why alternatives are too broad. Do not mistake a broad disable, permissive override, or speculative shim for an intent-preserving fix. Preserve modern paths and dynamic operating rules; put logically related changes within the *existing* patch. If no direct precedent exists, say so explicitly, and validate the minimum new behavior rather than making up an interface.

**Rank demonstrated precedents by actual technical equivalence, not superficial similarity:** (1) same chip, OEM board, firmware generation and failing command; (2) same Linux driver and exact upstream API/binding, including accepted upstream patches; (3) same vendor/chip family with documented failure and reviewed regression fix; (4) analogous upstream subsystem drivers and kernel interface contracts. For every candidate note *what was proven, under what conditions, what failed elsewhere, which behavior must remain unchanged, and the minimum test that could falsify the analogy*. Prefer an already-accepted upstream interface over any new shim. Explicitly check the upstream history for a **revert/regression** before copying any attractive one-line fallback. Example: brcmfmac country translation must use device-specific `brcm,ccode-map` instead of global trivial ISO→firmware rev0 mapping, because that universal fallback was reverted after BCM4359 AP regressions. [Exact matching precedent and citations](../research/MZ600_WIFI01_EXTERNAL_UPSTREAM_OEM_PRECEDENTS_2026-10-29.md).

**Current example:** [WIFI-01 comparative Broadcom `bcmdhd`, upstream cfg80211, Marvell `mwifiex`, Atheros `ath9k`, and maintainer evidence](../research/MZ600_WIFI01_EXTERNAL_UPSTREAM_OEM_PRECEDENTS_2026-10-29.md) explains why a firmware-current `GET_VALID_CHANNELS` list must not automatically become a permanent pre-registration hardware superset; genuine hardware constraints and mutable regulatory rules belong to different phases.

## Mandatory historical reuse gate (2026-10-28)

**Owner standing rule: Every new or newly reproduced defect MUST begin with an evidence-based search for past instances and prior solutions before designing or deploying another fix.** Do not rely on memory alone. This gate applies to every subsystem (BCM4329 Wi-Fi/BT/FM, SDIO, GPIO, power, device tree, ATAG MAC, BigPart, USB, recovery and cross-model tests), whether or not a GitHub issue already exists.

1. **Find related evidence first:** search the repo's dated checkpoints, research and source builders, [GitHub issue history](https://github.com/Olsens11/XoomLinux7/issues), previous patch revisions, upstream source and vendor/OEM reference behavior. Follow cross-links to actual raw/private receipts when needed, without copying sensitive contents into the public repository.
2. **Reconstruct what worked and what was abandoned:** list actual earlier inputs (board, firmware, NVRAM, country/revision, kernel commit and config), observed PASS/FAIL, rollback, and the *reason* a later revision changed the approach. A successful one-off lab-only workaround is not automatically a valid upstream fix; later experiments may have disproven its suitability.
3. **Classify equivalence:** same cause / related symptom but different cause / prior hypothesis disproven / older approach intentionally retired / truly new issue. State the strongest supporting evidence and uncertainty. Check source differences and GitHub provenance; don't infer “introduced by us” from a recently noticed symptom.
4. **Choose smallest necessary next experiment:** reuse the validated technique when still correct, update an existing logically scoped unsigned patch rather than inventing a fixup, or justify an independent patch only if the proven cause is independent. Never replay consumed one-shot markers or change regulatory/power settings to rediscover a known result.
5. **Record the gate in the issue and checkpoint:** add a concise **Historical lookup** section with exact links to earlier experiments and what they established, a **Why this solution still applies / no longer applies** analysis, and the next one-variable test. If nothing comparable was found, say which sources were searched and mark it as *no prior match found*, not proof no precedent exists. Keep project indexes, status and working source provenance consistent.

**Immediate example — WIFI-01 regulatory channel fallback:** [Oct26 v05](../checkpoints/MZ600_V064_HRI39_5GHZ_WLAN0_PASSIVE_CHANNELS_PASS_ESCAN_UNSUPPORTED_2026-10-26.md) and [May2012 V13](../checkpoints/MZ600_V13_2012_OEM_FIRMWARE_2G_5G_BANDLIST_PHYSICAL_PASS_CLEAN_2026-10-26.md) proved a *conservative lab-only* approach that sets `NO_IR` on all firmware-supported fallback channels, limits bandwidth to 20MHz and keeps disabled/DFS handling. [V28 Oct27](../checkpoints/MZ600_V28_NATIVE_CFG80211_SCAN_AFTER_LAB_GATES_REMOVED_2026-10-27.md) later intentionally removed the blanket NO_IR lab scaffolding for ordinary cfg80211 behavior; the missing full effective regulatory-domain verification remained open. [Oct28 r2 physical test](../checkpoints/MZ600_WIFI01_R2_OEM_2012_PERCHAN_PHYSICAL_AND_HISTORY_2026-10-28.md) found `per_chan_info` **failed 35/35**; consult all three precedents before deciding the next WIFI-01 revision.

## Milestone-to-upstream integration gate (mandatory, 2026-10-27)

**Review-source packaging preflight:** After every canonical review patch or `series` edit, run `python3 tools/validate_upstream_review_series.py` for LF-delimited ordering, manifest hashes and patch-stream integrity; run `bash -n scripts/qa_replay_upstream_review.sh` on tool changes. Then apply every member on a pinned clean kernel tree and run source-level `git diff --check` plus `checkpatch.pl`. Do not confuse a clean outer project `git diff --check` with checking a literal email-format patch's *applied* kernel diff. Re-run clean per-prefix ARM builds and full integration when source hunks change; metadata-only re-exports require equivalence and integrity rechecks. Record any failed attempts, exact tested revisions, and whether a reusable script was executed or only inspected.

**Objective:** Keep the full BCM4329/Wi-Fi/Bluetooth/SDIO/board implementation continuously reviewable. Do not defer patch reconstruction until completion of a whole-chip feature. A successful experiment is *evidence*, not automatically an upstream patch or a qualification of unrelated source.

For **every materially new result** (positive or negative physical finding, validated source fix, clean-build/replay milestone, firmware/board interface discovery, or newly rejected hypothesis), close the work in the **same development session / same documentation change**:

1. **Checkpoint:** Write or update a dated, immutable `docs/checkpoints/` record with exact machine/DUT and kernel/source revision, firmware identity where publishable, build configuration, artifact hashes, commands/tests, measured results, negative controls, scope, rollback and unanswered questions. Keep sensitive raw logs private; link only sanitized evidence.
2. **Classify and route:** Assign the finding to one stable logical work-item ID and maintainer track (WIFI, BOARD/DT, BOOT/ARM, SDIO/MMC, PWR/regulator/clock/GPIO, BT, STORAGE/block, or internal INTEGRATION). Identify relevant source paths, maintainers/list/tree using the current target tree's `MAINTAINERS` and `scripts/get_maintainer.pl`; mark uncertain routing **OPEN**, not confirmed.
3. **Patch decision:** Record **revise existing canonical patch / add independent logical patch / prerequisite binding or subsystem change / lab-only / no source change / deferred** with a technical reason. Never use chronological Vxx lab iterations as upstream patch numbers. Preserve the prior immutable snapshot and relevant upstream examples. If implementation is mature enough, revise the original focused RFC member now (not a trailing experimental fixup), while preserving correct prefix-by-prefix bisection.
4. **Evidence gates:** Update each affected work item's G01–G12 status in [submission requirements](../../patches/upstream/candidate/SUBMISSION_REQUIREMENTS.md), distinguishing exact-source physical tests from V31/lab analogues, standalone compile, full build, static check, regression and maintainer review. An unchanged patch may legitimately remain **OPEN**.
5. **Integration:** Update the whole-chip dependency/interaction ledger (Wi-Fi↔SDIO↔PWR↔BT↔BOARD), the current clean-source replay/manifest references if a patch actually changed, and the next engineering gate. Maintain separate **upstream review series** for independent maintainer domains and an **internal complete-device integration sequence** with exact revisions and hashes.
6. **Discoverability and state:** In the same documentation commit, update `docs/checkpoints/README.md`, local subsystem indexes, `docs/README.md` where necessary, `docs/status.md`, `runtime/PROJECT_STATE.env`, and the relevant roadmap/handoff so the latest validated state is obvious. Resolve stale top-of-file "latest" banners instead of adding contradictory ones.

**Definition of milestone done:** evidence recorded; logical ownership assigned; canonical-patch decision recorded; acceptance gates and dependency matrix refreshed; living status/indexes aligned; repository checks run. An unresolved gate must remain explicitly open with a next test and owner track. Never block the factual checkpoint on an unfinished patch, but do not mark the integration/documentation task complete without recording why the patch is pending.

**Patch-release discipline:** A patch series is an independently versioned review product: one problem per patch, coherent multi-file changes permitted, genuine upstream commit messages, correct target base, buildable prefixes, review evidence, DCO handled solely by the human. Bindings precede code that consumes them; board DTS normally follows and routes through SoC maintainers. Work on the existing branch/worktree according to the one-writer rule, and never automatically send email, sign off, force-push, reflash, or install a test image during milestone bookkeeping.
