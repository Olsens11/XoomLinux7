# Xoom Linux 7 — upstream-oriented logical patch decomposition

**Status 2026-10-27: design and review boundary, NOT a claimed constructed/passing submission series.**

## Owner's non-negotiable patch model

A final upstream series consists of **individual logical, bisectable kernel changes**, in a deliberate dependency order, each authored as a complete, clean implementation against the original upstream base plus the preceding logical series entries. **Do not present V21 → V22 → V23 ... as kernel patch dependencies**. Iterative experiments belong exclusively in lab/checkpoint documents. When a change is improved during development, revise/replace its original series member, not append a fixup patch describing the evolution. A new patch is warranted only for a genuinely distinct logical problem.

The current [four-file source integration snapshot](../../patches/upstream/candidate/series), commit `cf009ca`, has **clean sequential application**, but its boundaries **are NOT submission-review boundaries**. In particular, its `0004-wifi-...compatibility.patch` has ~680 lines, contains channel-discovery fallback, ESCAN transaction generation, Event69 terminal routing, and extensive `MZ600_V29_` diagnostic logs and runtime module parameters. It is a useful **lossless integration snapshot**, not a model final wireless patch. Keep it immutable as evidence until replaced by a complete source-equivalent *review series* (not stacked on it).

The Linux kernel [submitting patches guide](https://docs.kernel.org/process/submitting-patches.html), [Linux wireless submitting guide](https://wireless.docs.kernel.org/en/latest/en/developers/documentation/submittingpatches.html) and [posting guidance](https://docs.kernel.org/5.3/process/5.Posting.html) stress one logical purpose per patch, complete justification, maintainers' ability to review/bisect each step, and that final submission history need not resemble experimental development history. Multi-file changes can belong in one patch if they form one indivisible logical change.

A review-series group could be split by maintainer ownership into e.g. board/boot, storage and `wifi: brcmfmac` email series. This is not an excuse to stack iterative lab patches; dependencies, if any, arise strictly from the required source APIs and feature enablement. Never introduce a build break between the patches. Consider a preparatory interface/lifetime API as a separate patch **only when it is independently coherent and exercised**, not a dead preparatory scaffolding patch.

## What to EXCLUDE from the upstream patches

- `MZ600_Vxx_` logging throughout `cfg80211.c`/`fweh.c`, test-only sysfs/module parameters (e.g. `mz600_extra_events`, `mz600_terminal_owner`, `mz600_request_sync_id`, `mz600_generation` as debugging switches), broad event subscriptions, artificial timeouts, hardcoded channel36/5180MHz/NO_IR/forced-passive/500ms restrictions.
- Raw firmware/HCD/NVRAM, private MACs, SSID/BSSID/credentials, binary ARM module outputs, one-shot flash/COM9 transfer scripts, personal host paths, Debian root filesystem or initramfs installation scripts.
- Source comments describing V19/V21/V28 development or claimed upstream readiness. Commit messages must explain *what and why* in clean source context, not the journey.

## Construction and acceptance of **new** review-quality canonical series

1. Freeze hashes of current broad integration snapshot and physical evidence. Use it as the *target behavioral reference*, **not** as an upstream patch predecessor. Never physically remove the working p7/p8 Debian installation.
2. Start a **clean** kernel checkout at `xoom-linux/linux@2404d27378503b4df74ab2cb0a8b7cd6cf9d5fc3` and intentionally split by actual logical code, building focused commits. Unrelated experiments/lab probes must be filtered out before making each commit.
3. Run `git diff --check`, `scripts/checkpatch.pl`, `git format-patch`, DT binding/compile and exact ARM kernel+WCC+DTB compilation. Test `git am` on a separate clean checkout, then compile and (where safe) test **each prefix** of the series to preserve meaningful `git bisect`. Never claim first-pass clean application alone proves compile/run.
4. Compare final aggregate source diff with intended functionality. Distinguish intentional removal of lab code from missing essential compatibility changes.
5. Physically validate the final source series through normal cfg80211 network scanning, repeat scans, permitted association/authentication and link data flow, cancellation/races, and additional Xoom models; verify regulatory policy and hardware/firmware integrity.
6. Maintain one canonical review patch per work item, revised in place as its design matures. Leave all historically numbered experiments/checkpoints under the lab records only. Add genuine contributor's DCO signoff **only with explicit consent**, and submit nothing without authorization.
