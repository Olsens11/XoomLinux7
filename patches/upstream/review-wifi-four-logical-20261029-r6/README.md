## Proven source-level problem

`net/wireless/reg.c:wiphy_update_regulatory()` normally rebuilds legal channel flags from `orig_flags` before calling driver `reg_notifier`; `brcmf_translate_country_code()` returns `-EAGAIN` when ISO country abbreviation already equals the firmware value, causing the original notifier to skip the firmware's allowed-channel requery. On legacy BCM4329 firmware lacking `chanspecs`, that may omit reapplication of *currently valid firmware channels*. Country code is not legal permission; Broadcom's PHY `alpha2=99` lacks per-channel DFS/NO_IR metadata.

## Exact r5 → r6 changes (same WIFI-01 issue)

- `brcmf_bcm4329_legacy_channels()` now fetches/validates the bounded legacy channel list, allocates and stages **additive-only** restrictions, and commits using `flags |=` only after all required optional queries succeed or report actual native `BCME_UNSUPPORTED=-23`. A late native `BCME_NOTUP=-4` or transport/metadata query failure returns without applying a partial channel table. A `kcalloc` failure likewise leaves channels unchanged. `orig_flags` and preexisting cfg80211 restrictions are never cleared. **Unknown 5GHz metadata retains conservative NO_IR**.
- `brcmf_bcm4329_refresh_legacy_channels()` is a private BCM4329 helper that checks `chanspecs` with per-call raw-BCME provenance and invokes the legacy list only for actual firmware unsupported. A modern `chanspecs`-capable BCM4329 and unrelated modern chips retain their previous behavior.
- For **only BCM4329 and only the translator's `-EAGAIN` return**, `brcmf_cfg80211_reg_notifier()` attempts the legacy-only firmware restriction refresh instead of exiting immediately. No country SET is introduced for that path; a query failure is logged rather than treated as authorization to enable a channel. Existing behavior after a valid new country write is unchanged.
- WIFI-02, WIFI-03 and WIFI-04 retained **identical stable `git patch-id --stable` values** to r5 (respectively `f3640d66bb029408fd9bbd66d24b52873696b8e4`, `8c968d701aa204f86d0c62655a2e134092aeea10`, `a265bc9566a6f8fba96af95434d377c7863d0efc`). They are separate scan-state/readiness issues, not amended to accommodate this compatibility fix. BigPart remains a separate ninth patch.
