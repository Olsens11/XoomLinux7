# OEM Android reference scan proposal vs. Linux7 2.4GHz / original HRI39 5GHz completion evidence
Date: 2026-10-26. **READ/PLAN ONLY. No OEM tablet connected, no new scans, no driver tests, no firmware writes.**

## What the current physical scans actually prove

1. On installed Debian Linux7, **generic firmware BCM4329/3 version 4.220.48 (Sep 2 2011)** + normal brcmfmac firmware path, a single `iw dev wlan0 scan freq 2412 2437 2462 passive` returned a full result dump, command exit 0, 51,104 bytes and **19 BSS entries**. It is recorded at [2.4GHz scan physical checkpoint](../checkpoints/MZ600_V064_PERSISTENT_DEBIAN_BCM4329_WLAN0_PASSIVE_SCAN_AND_ORDERED_TEARDOWN_PHYSICAL_PASS_2026-10-26.md), with successful driver unload, no persistent change.
2. The actual modern `brcmfmac/cfg80211.c` normal ESCAN handler subscribes to firmware **BRCMF_E_ESCAN_RESULT event69**. On **terminal status SUCCESS**, it informs BSS and calls `brcmf_notify_escan_complete(aborted=false)`; its watchdog instead calls `brcmf_notify_escan_complete(aborted=true,fw_abort=true)`. Normal `iw scan` code distinguishes `NL80211_CMD_NEW_SCAN_RESULTS` from `NL80211_CMD_SCAN_ABORTED`; for an aborted scan it prints a message instead of dumping 19 entries. Therefore the observed normal 2.4GHz output is **strong evidence Linux considered the scan successfully completed**, consistent with actual event69. **No direct event69 capture or elapsed completion timing was taken; do NOT claim exact event69 hardware arrival proven.**
3. Conversely, **original OEM HRI39 firmware 4.218.248.20 (Jan 12 2011)** was tested on Linux7 via a separate legacy WLC_SCAN=50/RESULTS=51 channel36 NO_IR passive shim; v11/v12b returned 3-4 valid BSS but only at **~10 second modern escan timeout**, with firmware event26 mask readback ON but no event26 observed at post-header event classifier. The existence of cached results proves neither actual firmware terminal state nor event generation; this is why ISCAN is being researched.
4. The generic 2.4GHz scan unexpectedly included **two 2442MHz channel7 records** although requested ch1/6/11; that is BSS metadata, NOT proof the radio traversed ch7. Do not publish private SSID/BSSID/MAC captures or infer prohibited RF transmission.

## Why a spare stock Android Xoom can be a stronger reference

A **second, unmodified OEM MZ600 running Motorola Android** can show the authentic driver+firmware+Android completion *behavior* side-by-side and help discriminate event26 (legacy) versus `iscanresults` (status) versus host timeout. A native Android GUI/WEXT scan-complete broadcast alone **does NOT prove on-chip event26**, since it may be synthesized by the host when iscan reaches SUCCESS. Correlation with actual kernel logs/driver code and firmware identity needed.

Recommended safest diagnostic sequence, only after owner plugs in and authorizes observation:
- Prefer same model **MZ600**; MZ602/MZ604 may have different firmware/NVRAM/band/regulatory setup. USB data cable connected to approved Surface/Desktop; leave Android/firmware unmodified; enable ordinary USB debugging as needed.
- Read-only identity: `adb devices`, `adb shell getprop ro.build.version.release`, `adb shell getprop ro.build.fingerprint`, `adb shell getprop ro.product.device`, `adb shell uname -a`; determine actual BCM4329 firmware version, image SHA if filesystem access permits, matching factory region and driver revision. Do not assume it runs exact HRI39 just because it is a Xoom.
- Read-only baseline logs `adb logcat -v time`, `adb shell dumpsys wifi` if supported, `adb shell dmesg` if permitted; native Android UI Settings > Wi-Fi ordinary scan. Timestamp request start, UI/Android scan-finished indication, any DHD/WEXT/BRCM event26 and iscan status traces, number of BSS. Avoid unsolicited association or changing country, regrev, NV calibration, RF limits; normal OEM scan may be ACTIVE, so distinguish it from Linux7 passive scan before drawing timing or regulatory conclusions.
- If root/debug logging available, narrowly instrumenting the native host scan completion code **read-only logs only** could disclose event26 vs status; avoid changing stock drivers, kernels or radio just for observation. If no kernel event logging, UI results prove OEM scan completed *as viewed by Android*, NOT source of internal completion.
- Optionally observe normal OEM 2.4GHz and 5GHz capability, without forcing channels/no-IR TX or blanket RF tests; restrict experiments to what the stock firmware and native UI already supports.
- The key comparative matrix is: OEM Android with exact FW/driver/event or iscan evidence; Debian generic 4.220.48 2G modern ESCAN likely event69; Debian original HRI39 5G legacy 50/51 and timeout. Keep different firmware generations explicitly separated.

## Decision

Yes, native OEM observation can materially shorten research. Prefer one stock spare Xoom for **noninvasive baseline capture first**, not a new kernel patch. Use it to identify whether native Android completes by WLC_E_SCAN_COMPLETE (26), an ISCAN terminal status, or host-generated WEXT notification. Preserve the demonstrated Linux7 2.4GHz normal-scan success and 5GHz legacy scan results separately until on-chip completion is verified.
