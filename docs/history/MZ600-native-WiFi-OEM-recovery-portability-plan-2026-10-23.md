# Motorola Xoom MZ600 native Linux Wi-Fi — board-portability policy and OEM/recovery reference
Date 2026-10-23. **Reference and preparation only. No device updates or Wi-Fi state changes.**

## Core rule: DO NOT bake an identity into the kernel
A shared MZ600 Linux kernel, DTB and initramfs must NEVER include a reference Xoom's fixed MAC address, device-specific private credentials, SSID, WPA secrets or inherited connection state. Default must query physical hardware/OTP/SROM via upstream Broadcom `brcmfmac` when available. If the chipset needs a platform MAC or OEM per-device provisioning, resolve it **for the current tablet**, not from a different device. When MAC provenance is unknown, keep network unassociated; never silently use a shared template or random MAC as evidence of a production hardware address.

After future initial probe, read `/sys/class/net/wlan0/address` and `/sys/class/net/wlan0/addr_assign_type` and inspect `dmesg` MAC-related diagnostics. Compare against **that same** MZ600's stock Android MAC (read-only after controlled reboot), or trustworthy same-device OTP/factory source. Do not assume `addr_assign_type=0` alone proves correct factory identity; the firmware can have selected a configured address. Do not log full addresses in public artifacts.

## v06 Linux state, kernel analysis
- Replacement MZ600 serial 170061c243805617 currently running native Linux v06 RAM-only via `fastboot boot`, USB CDC serial COM9. Touch/grid/crosshair calibrated and physically verified. NEVER flash Android BOOT/TWRP RECOVERY. Original heavily customized reference Xoom serial 02804102421F7517 must remain untouched.
- Active DTS `linux-src/arch/arm/boot/dts/nvidia/tegra20-motorola-stingray-usbdiag.dts`: SDMMC2 wifi `mmc@c8000200` enabled, SDIO bus width 4, max-frequency 46153846, Broadcom `compatible = "brcm,bcm4329-fmac"`, regulator `vdd_wifi` gpio U4, pwrseq reset gpio U2, host-wakeup gpio U5, `vwlan1` voltage, Bluetooth combo GPIOs. This is a strong hardware starting point but successful probe under **modern kernel is not yet proven**.
- Built kernel `CONFIG_BRCMFMAC=m`, `CONFIG_BRCMUTIL=m`, `CONFIG_CFG80211=m`, `CONFIG_MAC80211=m`, MMC_SDHCI_TEGRA=y, SDIO=y, firmware loader=y. Tiny v06 initramfs doesn't load network modules, hence missing wlan0; merely changing to built-in modules will not guarantee successful firmware/power-up.
- In inspected current kernel `brcmfmac/firmware.c`, if `eth_platform_get_mac_address` succeeds it strips inherited `macaddr` from NVRAM and appends platform address. If it doesn't, file `macaddr` could be honored. In `brcmfmac/common.c`, firmware-reported `cur_etheraddr` is read and a known shared default MAC can be replaced by **random**, which is NOT the verified hardware identifier. Thus removing an inherited MAC is necessary but not proof of a successful hardware OTP read.
- Linux Wireless driver docs: brcmfmac SDIO requires separate firmware binary + board NVRAM. For 4329 upstream `brcmfmac4329-sdio.bin`; NVRAM `brcmfmac4329-sdio.txt` or compatible board-specific variant as indicated by driver requests. Use standard Linux driver, no binary Android proprietary userspace/legacy `wpa_supplicant` or `dhcpcd` required for initial probe.
- Plan for first limited Linux Wi-Fi diagnostic: build on known v06 with built-in brcmfmac/cfg80211, firmware via initramfs, MAC-free reference NVRAM; test only SDIO enumeration, firmware loaded, interface availability, reported MAC provenance and driver log; **do not associate, join a network, set Wi-Fi country or initiate DHCP** until same-device MAC verified and regulatory settings resolved. Keep USB serial as fallback and preserve nonpersistent boot.
- The upstream brcmfmac driver docs and code are publicly available in kernel and Linux Wireless; links were externally checked in user conversation. Regulatory settings `ccode` require deliberate audit; do not assume XY or US universally correct.

## Proven recovery Wi-Fi vs upstream requirements
- TWRP old Linux 2.6.39.4 already achieved WPA2 association, DHCP, online connectivity via original bcm4329 downstream driver and firmware. Recovery's `wlan0` and old Android userspace don't imply modern kernel's brcmfmac module will work without power/firmware/NVRAM adaptation.
- Proven recovery package architecture and OS-specific DHCP hooks valuable for logic and QA, not code portability; no reason to bring Android Bionic/linker/daemon into native Linux.
