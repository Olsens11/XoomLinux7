# BCM4329 Event69 completion: V21 evidence-to-upstream design model (2026-10-27)

**Stage: engineering RFC / source audit, NOT an applied kernel patch and NOT an authorized upstream submission.** Applies to the experimental Motorola Xoom MZ600 Linux 7 brcmfmac port. Read the [V21 physical checkpoint](../checkpoints/MZ600_V21_TERMINAL_OWNER_LAB_SWITCH_AB_PHYSICAL_PASS_2026-10-27.md), [V20 ABI investigation](MZ600_V20_EVENT_HEADER_ABI_SOURCE_AUDIT_2026-10-27.md), [patch integration ledger](MZ600_BCM4329_LINUX7_WHOLE_CHIP_PATCH_INTEGRATION_LEDGER_2026-10-26.md), [release gates](../plans/MZ600_BCM4329_LINUX7_MULTIDEVICE_PATCH_SERIES_RELEASE_GATES_2026-10-26.md) and canonical [cross-host transfer procedure](../process/DESKTOP_SURFACE_XOOM_ARTIFACT_TRANSFER.md) before acting.

## 1. Separate measured facts from hypotheses

- **Settled:** The actual 2012 Broadcom BCM4329 firmware issues firmware Event69 (`BRCMF_E_ESCAN_RESULT`) with `status=BRCMF_E_STATUS_SUCCESS`, promptly during/after passive scan. V18 observed it at ingress. V19 proved it can pass through queue to the worker yet be discarded when a decoded `bsscfgidx` maps to a missing interface. V20 captured 17 Event69 headers all reporting **message version 2** and showed an ordinary terminal with index0 produces normal `cfg80211_scan_done(aborted=0)`.
- **Settled:** V21 used one exact ARM kernel module (350476B SHA `aa222e2bebe47b76649dacabeddfd3d6fe823813a74c267b73c82813fcd13741`) with `mz600_terminal_owner` toggle default OFF, unchanged 2012 firmware, fixed `mz600_extra_events=0`. OFF invalid terminal `ifidx=2 bsscfgidx=16` failed at worker and waited **10476ms** for watchdog. ON invalid terminal `1,1` and `2,16` both logged **`TERMINAL_OWNER_CHECK eligible=1` → `TERMINAL_OWNER_DELIVER` → ordinary cfg80211 scan_done aborted0** (1642ms and 1232ms; 3 userspace BSS each). Three normal-index0 successes did **not** exercise the fallback. All six trial rollbacks and final independent original-runtime audit PASS. No firmware/chip modifications.
- **Settled:** All *six terminal packets* in the V21 private numeric traces report **event message ver2, `datalen=12`, `pktlen=94`**, regardless of index values. V21 terminal (`ifidx,bsscfgidx`) sequence: `(2,16)`, `(42,0)`, `(1,1)`, `(0,0)`, `(2,16)`, `(0,0)`. The same terminal packet-length pair accompanies good and unresolvable interface attribution. **A variable-length packet-offset theory alone is not established**; neither is firmware field corruption. Some other V20/V21 partial-result packets had different lengths and ambiguous index interpretations, but we do NOT need to correct all partials to close the immediate timeout gap.
- **Not settled:** Is the version-2 interface index *actually* generated incorrectly by this firmware, or read/interpreted incorrectly by the host? No original trusted raw reference yet proves intended meanings for these specific trailing bytes. The v1-missing-two-bytes explanation does not fit the observed version-2 terminal messages. **Do not claim wrong transmitted indices as fact**.
- **Not settled:** Does firmware echo scan `sync_id` correctly in the 12-byte terminal payload, and does it accept changing that ID across scans? The current Linux7 ESCAN request writes `sync_id=0x1234` unconditionally; nothing in prior V21 logs records the returned payload sync ID. **We have not demonstrated scan-generation correlation.**

## 2. Verified Linux7 source contract: event and scan paths

Source tree `v064-bigpart-linux/drivers/net/wireless/broadcom/brcm80211/brcmfmac`:

1. `core.c`: `brcmf_rx_frame` / `brcmf_rx_event` call `brcmf_rx_hdrpull` then `brcmf_fweh_process_skb`. `fweh.h` validates Broadcom OUI/subtype, then passes event to `brcmf_fweh_process_event`. `fweh.c` validates event type, subscription, length; copies the version-2 `brcmf_event_msg_be`, payload, and queues to `brcmf_fweh_event_worker`.
2. `fweh.c`: before dispatch it bounds-checks `event->emsg.bsscfgidx` against `BRCMF_MAX_IFS`, then normally resolves `drvr->iflist[emsg.bsscfgidx]`. If out of range or absent, the real SUCCESS never reaches `brcmf_cfg80211_escan_handler()`; this is the proved Linux-side failure point.
3. `cfg80211.c`: `brcmf_cfg80211_scan` stores the active `cfg->scan_request` and BUSY state, then `brcmf_do_escan` records the **owning `cfg->escan_info.ifp`**, sets ESCAN_SCANNING and starts firmware escan. This is *already the Linux source of truth* for which interface owns completion.
4. `cfg80211.c`: existing `brcmf_cfg80211_escan_handler` handles nonpartial SUCCESS by delivering cached BSS and calling `brcmf_notify_escan_complete(cfg, ifp, false, false)`. That routine clears `cfg->scan_request`, cancels the watchdog and invokes ordinary `cfg80211_scan_done(...aborted=false)`. No fake completion, global remapping or timer shortcut needed.
5. `fwil_types.h`: `struct brcmf_escan_result_le` starts with 12-byte fixed envelope `__le32 buflen`, `__le32 version`, `__le16 sync_id`, `__le16 bss_count` followed by variable BSS data. All six V21 terminals have declared **12-byte payload**, the exact fixed envelope size. This makes **numeric sync_id readback a concrete, bounded, relevant next check**, not a new search for Event69. Read at offset 8 (little-endian) only after validating `datalen >= 10`; full fixed header can be checked at 12. Distinguish payload framing verification from assuming those bytes are meaningful.
6. The existing Linux escan request sets `params->sync_id = cpu_to_le16(0x1234)` in `brcmf_run_escan`. Because it is reused, matching `0x1234` alone **does not reject a delayed SUCCESS belonging to an earlier scan**. A unique/rotating scan ID would be needed for transaction identity, if the firmware supports this.
7. Other relevant implementations: Fuchsia's Broadcom-derived `brcmf_cfg80211_is_valid_sync_id` checks the returned result's sync_id against active `scan_sync_id` after payload bounds checks. This is **design precedent**, not proof that our chip echoes nonconstant IDs or that Fuchsia's concurrency model is directly portable. Reference: https://fuchsia.googlesource.com/fuchsia/+/6bd39c01aafd48a93bf9a79e86d462f9a5f0181b/src/connectivity/wlan/drivers/third_party/broadcom/brcmfmac/cfg80211.cc ; upstream Linux example retains hardcoded 0x1234 in contemporaneous scan-parameter work (https://lists.openwall.net/linux-kernel/2026/09/25/1149).

**Packet-size caution:** `pktlen94 - datalen12 = 82`, versus the 72-byte declared modern complete Ethernet/Broadcom/event envelope; there are 10 extra received bytes not explained by this simplistic subtraction. It is NOT established whether these are transport padding, a trailer, or another framing detail. Do not move event field offsets or assert data corruption from the difference alone; successful BSS109 payload decoding is known and both good and bad terminal indices share the same lengths.

## 4. Proposed minimal production control flow (conceptual, NOT C patch)

- Ordinary valid interface indices continue through the existing event-worker dispatch **unchanged**.
- Only for matching legacy device/firmware scope, genuinely validated version2 `BRCMF_E_ESCAN_RESULT` with **status SUCCESS**, and **only when** ordinary bsscfg lookup would fail, ask the cfg80211 scan owner helper whether the queued payload is a terminal for the **current, live** scan.
- The helper owns checks on `cfg->scan_request`, `BRCMF_SCAN_STATUS_BUSY`, `escan_info.escan_state`, `cfg->escan_info.ifp`, instance lifetime, one-primary-interface/no-P2P, device teardown or cancel, and—*if proven supported*—current firmware-reported `sync_id` with sufficient bounds checking. It returns the valid scan owner or NULL; it never modifies event bytes or invents success.
- If allowed, dispatch through **the normal registered Event69 handler** and let the unchanged `brcmf_notify_escan_complete` deliver scan_done. Keep the fallback exceptional; do not append an unverified second completion path. If not allowed, retain normal drop and watchdog semantics.
- Do not permit fallback for partial status8, aborted/canceled statuses, unrelated events, multiple active interfaces or a mismatched/stale scan ID. Use the minimum protected cross-layer helper/API required to respect ownership; avoid accessing transient scan-state fields from the event layer without considering synchronization.
- Tests should explicitly model cancel-before-terminal, timeout-before-terminal, terminal-after-next-scan, duplicate terminal, null owner, multiple ifs/P2P, valid index, wrong chip/FW, undersized payload and firmware ID mismatches. Existing V21 physical tests are the baseline, not repeated proof that Event69 exists.

## 5. Incremental qualification gates; do not expand the project into redundant discovery

**Gate A — offline source and trace model (current):** completed static source audit above; V21 original six-trial private evidence secured; source and installed module untouched. Documented transfer SOP established.

**Gate B — *only* additional wire fact required:** from a fresh controlled passive scan, capture *numeric* firmware-returned terminal `sync_id`, bounded `buflen/version/bss_count`, with module logging in RAM (no SSIDs/MAC). Verify it agrees with firmware scan request `0x1234`; ideally also match across accepted partials, but not required to rediscover scan completion. Do **not** modify firmware. A second test with varying host-generated sync IDs is warranted **only if Gate B confirms echo** and the experiment is reversible and safe. This observation may falsify the preferred ID-based design; if so, revise and document a more conservative race-safe fallback.
 
**Gate C — exact-ABI minimal code and deterministic edge tests:** extract a standalone narrow source change separate from debug build scaffolding. Add KUnit or focused model tests for interface selection and late/duplicate/canceled events. If changing sync ID, review concurrency and generation-wrap semantics, test 2.4/5GHz and firmware variants. Verify every revision builds and sources/modules restore.
 
**Gate D — physical regression:** A/B the smallest candidate with same module and verified firmware, 5GHz and 2.4GHz, valid/missing/out-of-range terminal routes, cancellation and post-timeout, and later BT coexistence/other Xoom variants. Retain one-time trial IDs, independent rollback, and private logs. No upstream signoff without owner authorization.

## 6. Engineering conclusion

**What the data establishes:** Linux *already has* the right scan-completion state machine and scan owner. The defect arises at routing a genuine Event69 terminal to that state machine. The physical V21 fallback confirms that preserving the genuine terminal and assigning it to an *appropriate live owner* resolves the observed timeout. **An elegant permanent correction should preserve these boundaries and exploit verified scan identity rather than blanket interface remapping**.

**Still unknown:** the actual semantic origin of odd version2 index bytes, returned sync_id semantics, and correctness through cancel/reset and multi-interface lifetimes. No claim that the preferred production approach is implemented or physically tested.
