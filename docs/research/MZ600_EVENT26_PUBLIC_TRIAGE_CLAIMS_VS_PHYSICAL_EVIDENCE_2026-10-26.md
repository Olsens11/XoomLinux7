# BCM4329 HRI39 event-26 online triage claims cross-checked against XoomLinux7 physical tests and source

Date: 2026-10-26. Research-only; no Xoom access, no new RF scan, no module/kernel build or change.

## Why this note exists

An external Google-supplied answer suggested (1) event mask missing, (2) SDIO RX interrupt delivery failure, and (3) firmware scan hang; it proposed `iw ... scan freq 2412` and cited `seemoo-lab/nexmon/issues/85`.

## Audited facts

1. **Missing mask bit is already excluded in the tested HRI39 state.** Real v12a and v12b physical tests read `event_msgs` from HRI39 firmware with `rc=0 len=27 registered=1 driver_bit=1 fw_bit=1 map=0`. `WLC_E_SCAN_COMPLETE` is event **26**, bit index `26%8=2` in byte `26//8=3`; readback bit ON. `brcmf_fweh_activate_events()` uses `brcmf_fil_iovar_data_set(ifp, "event_msgs", ...)`, not the external response's alleged `brcmf_c_set_join_pref` entrypoint, and `brcmf_fext_handle_scan_complete` had no identifiable implementation in public code search. An enabled bit requests a notification *if* firmware generates it; it doesn't force scan-engine generation.
2. **SDIO event delivery remains unknown.** The v12b experimental BCM4329 numeric counters at `brcmf_fweh_process_skb()` and all later classifiers were **zero before** ioctl50 and at modern ~10s escan timeout. This alone cannot distinguish absent firmware-generated event, SDIO transport/hdrpull loss, unexpected path, or event emitted outside the observation period. Neither failed OOB IRQ nor `-ETIME=-62` was demonstrated by these tests. Other event types cannot be presumed available during an otherwise idle, unassociated passive scan.
3. **The suggested short scan was already performed, under more precisely scoped radio rules.** The Xoom physical experiment used the original HRI39 4.218.248.20 firmware in RAM, live per-device MAC and matching calibration, on a single NO_IR, non-DFS **5180MHz channel36** passive scan: ioctl `WLC_SCAN=50 rc0`; firmware result `WLC_SCAN_RESULTS=51 rc0 version108 1632 bytes BSS3`, all 3 BSS structurally valid and delivered to cfg80211/`iw`, zero probes. Therefore a broad multi-channel/DFS traversal hang is not an explanation of this particular single-channel test. However result presence is **not a proven scan-termination state**. `iw ... scan freq 2412` would change band and firmware/regulatory operating conditions, and isn't an equivalent controlled comparison.
4. **Critical omitted fourth cause: scan completion need not equal event26 transmission.** Public Broadcom internal WLAN scan-engine `wlc_scan.c` revision Dec 23 2010 (source mirrors, NOT proven exact HRI39 on-chip firmware) clears results, marks scan active, iterates dwell passes, returns home, sets `in_progress=FALSE`, invokes `wlc_scan_callback(...SUCCESS)`, which in turn invokes a registered callback pointer; an additional *direct* `wlc_bss_mac_event(WLC_E_SCAN_COMPLETE ... SUCCESS)` is inside `#if defined(MACOSX)`. 2012 internal scan source has same gate; abort/dead-chip event26 occurs outside that success gate. The actual callback target can still generate events on non-Mac firmware, so **not a categorical assertion that HRI39 never emits event26**.
5. **Modern Linux `brcmfmac` expects another event for its modern escan path.** Public current `cfg80211.c` `brcmf_init_escan()` registers `BRCMF_E_ESCAN_RESULT=69` through `brcmf_fweh_register`, not `BRCMF_E_SCAN_COMPLETE=26` in the unmodified normal escan lifecycle. Our compatibility shim issues legacy `WLC_SCAN=50` while original modern escan timer remains in control. This is a **protocol/lifecycle mismatch**, not evidence of physical interrupt failure. Experimental v12a/v12b specifically registered event26 to observe it, and it still did not arrive.
6. **External reference was unrelated.** `https://github.com/seemoo-lab/nexmon/issues/85` is titled **"Error with make on RPi3"** (June 2017); issue reports missing `bison` when compiling Nexmon. It does not document BCM4329 event26 receive path.

## Decision and next source-first step

Do **not** rerun consumed v12a/v12b physical one-shots, claim OOB IRQ broken, or shorten 10s timeout based on BSS counts. Continue source-first audit of the **specific callback registered by legacy `WLC_SCAN` command 50** in contemporaneous Broadcom scan engine, then whether that callback in an SDIO dongle/BCM4329 firmware configuration triggers event26 or another firmware-defined terminal event. Compare HRI39's firmware image evidence carefully. If this indicates actual event generation, inspect host SDIO channel demultiplexing/hdrpull and IRQ counters with a single distinct, observation-only, owner-operated experiment. All firmware, MAC, RF regulation, generic firmware and other-device release guards remain in effect.
