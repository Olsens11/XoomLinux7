## Physical Bluetooth steps and findings

1. Original BCM4329B1 HCD private firmware: **17,332 bytes**, SHA-256 `7fbab01012c909b9b2de0fda3a76c43fa1c5c150e08642d7d1dbaf4d5ebf887c` from Desktop private path `/home/xoomdev/xoom-linux-rom/private-firmware/BCM4329B1.hcd`. Confirmed same hash on Desktop Windows temporary staging, transmitted via SOP HTTP port 43157 to Surface private capture `C:\Users\olsen\xoom-linux-rom\captures\MZ600-Review9-BT-Private-20261028-A\BCM4329B1.hcd`, independently hashed Surface. The one-shot HTTP server and intermediate Desktop staging were then **closed/removed**. No firmware bytes in Git/public artifacts.
2. Transferred HCD over released COM9 as **29 bounded base64 serial writes to /tmp**, then decoded and checked full size and SHA on Xoom. Only after matching hash, `install -D -m 0644` to **p10** `/lib/firmware/brcm/BCM4329B1.hcd`. Device rehash and file metadata check **PASS**. Cleaned RAM staging; Wi-Fi remained connected. This is a persistent **p10 firmware file only**, not a firmware flash, NVRAM rewrite or loaded patch.
3. `btmgmt --index 0 power on` **PASS**: HCI reports `powered ssp br/edr`. The Surface adapter was connectable but not discoverable by default. Windows' preexisting cached Bluetooth device did **not** match the live Linux controller address; never assume old pairing.
4. Wi-Fi remained `GENERAL.STATE:100 (connected)` with `wlan0 UP,LOWER_UP` **during simultaneous HCI power-on**. This is one coexistence/power-management observation, **not** a validated concurrent Wi-Fi/BT traffic regression.
5. First generic `btmgmt find` returned `status 0x0c (Not Supported)`. Review of BlueZ source showed default discovery requests **BR/EDR + LE**; this BCM4329B1 advertised BR/EDR but **no LE**. Corrected test to `btmgmt --index 0 find -b` (BR/EDR only); it returned **Discovery started** / `hci0 type 1 discovering on`, then ended without finding Surface. Thus do **not** call classic scanning unsupported; initial failure was the wrong transport mix. Source context: https://kernel.googlesource.com/pub/scm/bluetooth/bluez.git/+/refs/tags/5.64/tools/btmgmt.c .
6. On Surface, used Windows native Bluetooth APIs to identify exact adapter and run bounded device inquiry. Xoom was briefly made discoverable and pairable (120-second discoverability timeout); Windows inquiry saw other cached/nearby devices, **not live Xoom**. Surface Windows discovery temporarily enabled for reciprocal Xoom BR/EDR-only scan then **restored to original OFF** with independent API state check. No other devices paired.
7. Attempted direct Xoom pairing only to the **verified Surface adapter address**, `timeout 16 btmgmt --index 0 pair -c 3 -t bredr [PRIVATE_SURFACE_MAC]`: kernel MGMT outcome **`connect failed (status 0x04, Connect Failed)`**. The process wrapper returned shell exit code 0 despite the **pair operation failing**; never classify as a pairing pass. `bluetoothctl info [PRIVATE_SURFACE_MAC]` reported **Device not available**. Wi-Fi still connected.
8. After installing the HCD file, a controlled **HCI power off → on** succeeded and Wi-Fi remained connected; **no new HCI firmware patch-load message** appeared. This proves that power-cycling an already-registered HCI controller did not rerun firmware setup, not that the file is malformed. We did **not** unbind/rebind `hci_bcm` or unload modules while the owner was away because previous OEM shared `WL_REG_ON`/`BT_REG_ON` and U4/I7 resource ownership are unqualified for risk-free unattended reprobe.
9. Final cleanup: `bluetoothctl discoverable off`, `pairable off`, `btmgmt power off`; `btmgmt info` final **current settings: connectable ssp br/edr** (no `powered`), `bluetooth.service` active but **disabled**, NetworkManager active and `wlan0` still connected, OEM HCD p10 SHA still correct, COM9 released. Windows Surface Bluetooth **non-discoverable** restored and host HTTP server stopped. No partnership/bond was established.
