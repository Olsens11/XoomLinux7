# MZ600 nine-patch upstream provenance and latent-issue audit — 2026-10-28

## Question, methodology, limits

The owner requires an explicit distinction between **(1) reported upstream Xoom Linux defects, (2) defects or limitations already present in upstream code, regardless of whether maintainers noticed or filed them, (3) newly discovered problems unrelated to our diffs, (4) regressions actually caused by our patches, and (5) risks suggested by code inspection but not proven at runtime**. An unsigned development candidate is **intentionally not ready for submission**; the human owner signs off **only after** all acceptance gates, not before.

- **Upstream source**: [xoom-linux/linux](https://github.com/xoom-linux/linux), `main`, directly rechecked via `git ls-remote` on 2026-10-28: `2404d27378503b4df74ab2cb0a8b7cd6cf9d5fc3`, identical to our pinned base. **Our exact nine-commit integrated tip**: `507eb069df819cb5cc801ad8be096f70d9ca7609`.
- **Upstream issue tracker**: Public GitHub REST repository metadata on 2026-10-28: `has_issues=true`, `open_issues_count=0`. Direct `GET /repos/xoom-linux/linux/issues?state=all&per_page=100` returned **zero issues**, and GitHub issue-search queries for BCM4329, Wi-Fi, Bluetooth, SDIO, Xoom and Tegra returned no matches in this repository. This establishes **no reports filed there as of inspection**, **not** “upstream code has no bugs” or “maintainers never noticed.” `/issues` does not include closed issues missing from a snapshot query? `state=all` was explicitly requested and no pages existed. Search current tracker again before a future contribution.
- **Other hardware and vendor trackers**: Similar BCM4329 or Broadcom reports on unrelated boards are only engineering references; they are **not** issue reports against xoom-linux/linux and are not automatically reproducible on our Tegra20/MZ600.
- **Evidence method**: Compare original `git show <base>:<file>` against integrated code, exact `git blame` where possible, inspect original Recovery HRI39 and Linux V31 lab checkpoints, audit source changes and contracts, compare on-device nine-build module hashes, and cross-reference latest read-only COM9/Surface WLAN observations. Do not claim any untested patch-internal branch passed from general network connectivity.
- **Safety**: This audit was **source/read-only**. No new radio scan or transmit configuration, no firmware changes, no module reload, no boot/partition change. Private MAC, SSID, NVRAM, credentials and firmware remain outside public repository.

## Source-location observations (reproducible on exact tree)

- `drivers/net/wireless/broadcom/brcm80211/brcmfmac/cfg80211.c` around **7849–7891**: baseline `WLC_GET_BANDLIST` decides existence of 5GHz `wiphy->bands[NL80211_BAND_5GHZ]`; untouched by our nine changes. `brcmf_construct_chaninfo` around **7138–7146**: new BCM4329 legacy channel filter only operates on bands already created; cannot produce Band 2 itself.
- Same file around **3304–3336**: baseline unchanged unsupported `BRCMF_C_GET_ASSOCLIST` handler. This is stronger evidence of a known-to-developers legacy firmware limitation than absence of a GitHub issue.
- Same file around **7060–7113**: our `brcmf_bcm4329_legacy_channels()` retrieves bounded `BRCMF_C_GET_VALID_CHANNELS`, validates count and channel number, ORs bandwidth restrictions but **does not fetch `per_chan_info`**. Normal branch around **7220–7250** requests that information and applies firmware radar/passive restrictions. Source difference is directly proved; safety consequence not yet.
- `arch/arm/boot/dts/nvidia/tegra20-motorola-xoom.dtsi` around **1274–1282** inherited `max-speed=<3375000>`; original `tegra20-motorola-wingray.dts` at baseline has same value. `drivers/bluetooth/hci_bcm.c` already requests high-speed controller clock above 3Mbps.
- `arch/arm/boot/compressed/atags_to_fdt.c` added `stingray_mac_atag_to_fdt()` with `fdt_setprop` return unused. It appears inside a shared boot decompressor; review board-identity restriction and actual FDT property on target.
- `block/partitions/efi.c` new opt-in `xoom_bigpart_geometry`, `xoom_bigpart_emmc`, `xoom_bigpart_factory_gpt` and entry rewrite. Default-disabled and geometry guards appear in source, but fail-closed negative physical tests still OPEN.
- Git blame showing inherited DTSI lines attributed to **our copy commit** is not proof that the *property value* was introduced by us. Compare against the baseline original Wingray DTS too.
