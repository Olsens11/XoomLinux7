# MZ604 Wingray upstream-first Linux 7 — physical unlock and bootloader rejection

**Date:** 2026-10-29. **Board:** Motorola Xoom MZ604 Wi-Fi-only (`wingray`, fastboot `xoom-wifi`). **Work item:** W1 / [issue #18](https://github.com/Olsens11/XoomLinux7/issues/18). **Maintainer track:** ARM Tegra board/boot handoff (internal physical baseline only; **no Linux source patch justified**). **Hardware status:** **UNLOCK PASS**, **RAM-only fastboot boot FAIL twice**, **upstream kernel execution NOT OBSERVED**. The same tablet returned to its stock Android 4.1.2 after a normal reboot. Full Debian/Wi-Fi runtime remains untested.

## Baseline and privacy

- Newly acquired MZ604 dedicated development DUT, stock Android product `wingray`, stock Android build `JZO54K/485486`, bootloader `1050`, battery originally 100%. Owner explicitly confirmed no preexisting user data needed; requested continuing with this development unit.
- ADB `ro.product.device=wingray` and fastboot `product=xoom-wifi` matched. Original bootloader was `secure=yes`, `unlocked=no`. Target-specific `fastboot oem unlock` was requested, confirmed using the tablet's hardware buttons, and host reported **OKAY**. Independent `fastboot getvar unlocked` returned **yes**. Unlock wiped old userdata; **no fastboot flash** performed.
- Prior to unlock, read-only host captures of the MZ604's native Wi-Fi calibration and station/APSTA firmware were saved in private Surface storage and SHA-checked. Their content, per-unit identity, raw logs and serial are not in public Git. See W1 issue history for sanitized file-size information.
- Source: **unchanged** upstream kernel `xoom-linux/linux@2404d27378503b4df74ab2cb0a8b7cd6cf9d5fc3`, original `tegra20-motorola-wingray.dtb`, fresh Debian ARMHF image/associated modules already built and verified offline. [Original complete build/packaging manifest](../rfc/bcm4329-upstream-first/BASELINE_BUILD_AND_USERSPACE_2026-10-29.md). Zero code modifications.
- Surface fastboot client **37.0.1-15733141**, protocol `version: 0.4`. ADB and fastboot each detected the correct MZ604 at the appropriate stages.

## Canonical artifact transfer and first two boot attempts

The required [Desktop→Surface transfer SOP](../process/DESKTOP_SURFACE_XOOM_ARTIFACT_TRANSFER.md) was consulted after an initial ad hoc HTTP attempt was identified as a workflow deviation and that server shut down. The documented procedure used **port 43157**, original desktop LAN address, a fresh per-trial temp-only staging directory, direct Surface `Invoke-WebRequest`, and an independent second-host hash/length verification. The first SOP transfer attempt encountered Windows inbound firewall blocking; owner enabled a port exception. Second attempt succeeded, and desktop server process identity was verified before targeted shutdown and listener-closed confirmation. No private firmware was served or transferred by HTTP.

Original image: `MZ604-WINGRAY-UPSTREAM-RAMONLY-UNTESTED.img`; 5,892,096 bytes, SHA-256 `9be975cbe4ed6ee8ee3b362775b6d36159ea10b87ebf22cb07d2662eb5c9877c`. SHA verified on desktop and Surface both before first temporary boot and again before controlled retest.

1. **Trial 1** after on-device unlock: verified fastboot product/unlocked and invoked `fastboot -s <private-id> boot <hash-verified MZ604 image>`. Host reported **Sending boot.img (5754 KB) OKAY [0.550s]**, then **Booting FAILED (remote: '(00000008)')**. Bootloader remained fastboot-responsive; **no Linux boot observed**.
2. One-variable discriminator: `fastboot reboot` to stock Android, which came up through ADB. Reentered fastboot via ADB, independently checked `product=xoom-wifi`, `unlocked=yes` and same exact SHA. **Trial 2** with unchanged image reported **Sending boot.img (5754 KB) OKAY [0.557s]** then the **same `(00000008)` rejection**. Subsequent ADB later detected the stock Android device again. This disproves a transient immediate-post-unlock-only explanation. Stop repetitive retries.

## Comparison with prior work and interpretation

- Compared the original candidate's legacy Android boot header against earlier MZ600 image builds that historically passed temporary fastboot boot (v034 and 2026-10-25 Stage-A). Fields matched: `ANDROID!`, page size **2048**, kernel load address `0x10008000`, ramdisk `0x11000000`, tags `0x10000100`, second `0x10f00000`, compressed ARM zImage prefix. Original MZ604 candidate used the unchanged original upstream Wingray DTB appended to ARM zImage. This **rules out an obvious header-address/page-size discrepancy**, not every board-specific or device-side boot policy difference.
- Web prior-art check found official AOSP Motorola Xoom unlock/fastboot documentation and physical MZ604 flashing examples, but **no authoritative exact mapping for Motorola bootloader code `00000008`**. Do not claim its meaning; it may be an unsupported command, image acceptance issue, or another private Motorola condition. Successful image *download* does not establish successful execution. Do not equate the negative boot result with a Linux kernel, DT, SDIO or BCM4329 defect.
- Static quality defect independently discovered in original MZ604 **lab-only** 2026-10-29 RAM-only cpio generator: it staged an empty `/dev`, unlike the established `phase1/pack-initramfs.py` that explicitly creates `/dev/console` and `/dev/null`. The missing character nodes cannot explain the observed bootloader rejection before kernel execution, but might limit PID1 console/boot reliability if boot succeeds. Preserve old image/hash as exact failed-trial evidence; do not retrofit it.
- **Corrected offline candidate, NOT transferred or booted**: use existing canonical `phase1/pack-initramfs.py`, same original freestanding MZ604 PID1 (4608 bytes) and original unchanged kernel/DTB. Output `/home/xoomdev/xoom-linux-rom/rfc-wingray-baseline-bootprep-v2-20261029/MZ604-WINGRAY-UPSTREAM-RAMONLY-V2-OFFLINE-UNTESTED.img`; SHA-256 `48b13fec35dc489b169d2ed0d2e7640b1ef7a66e325482775b383bc9de7c9bd0`. Corrected cpio gzip SHA-256 `cb078a724af6b2f1503bd64360753d871e4cc30de16a68eedd969ee9cd814128`. `cpio -itv` confirmed `dev/console` char major5/minor1 and `dev/null` major1/minor3. Only host-side binary packaging changed, **no kernel tree patch**.
