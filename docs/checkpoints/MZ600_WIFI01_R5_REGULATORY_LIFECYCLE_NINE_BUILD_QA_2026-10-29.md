## What exact pinned Linux 7 source demonstrates

Pinned upstream source: `xoom-linux/linux@2404d27378503b4df74ab2cb0a8b7cd6cf9d5fc3`. `brcmf_cfg80211_attach()` applies the Broadcom custom regulator `brcmf_regdom alpha2=99` and registers the PHY **before** `brcmf_setup_wiphybands()` reads firmware channel capabilities. `net/wireless/core.c` snapshots `orig_flags` on `wiphy_register()`. These immutable original flags are used by `net/wireless/reg.c` when recomputing restrictions and must **not** be overwritten with a **country-dependent** `WLC_GET_VALID_CHANNELS` list. See [Linux Wireless primary regulatory rules](https://wireless.docs.kernel.org/en/latest/en/developers/regulatory/processing_rules.html).

For an **accepted USER or COUNTRY_IE regulatory update**, `wiphy_update_regulatory()` handles the band using registration-time `orig_flags` plus applicable signed-regdb rules **before** calling the driver's `reg_notifier`. Then original `brcmfmac` may update firmware country and reread channel list. This is an available legal channel *restrict/reenable* path and overturns the earlier blanket assertion that firmware-disabled flags are inherently permanently stuck. It is not true for all hint types: `REGULATORY_CUSTOM_REG` **CORE** initiator can call notifier with *no band recomputation*, and notifiers may exit early.

`reg_get_regdomain()` chooses the PHY's custom `99` domain for initiators other than USER/COUNTRY_IE; `brcmf_regdom`'s 5GHz entries do **not** contain per-channel DFS/NO_IR restrictions. Therefore global US seen in `iw reg get`, native `country` value, or a valid OEM channel list does not, on its own, establish the effective per-PHY legal DFS/passive policy. Retain conservatively applied legacy `NO_IR` on unknown-metadata 5GHz rather than declaring TX safe.

**Additional source-only unresolved lifecycle risk:** `brcmf_translate_country_code()` can return `-EAGAIN` for an already-matching country abbreviation; `brcmf_cfg80211_reg_notifier()` then returns **without** rerunning `brcmf_setup_wiphybands()`. If a normal regulatory update recalculated flags first, the firmware-only allowed-channel list might not be reapplied on that path. This is a **potential source-level gap, not yet reproduced on actual BCM4329**. A failed/unsupported country translation also skips channel refresh. A patch must not blindly call the existing modern `chanspecs` path because that code can assign `channel->flags` rather than only further restrict: verify actual firmware behavior and prevent regulatory relaxation first. Partial channel mutation during late error is also unresolved. These require a separately isolated, proven one-logical-boundary correction **within WIFI-01 if causal**, not a new generic regulatory engine.

## Exactly what r5 updates

- In `brcmf_bcm4329_legacy_channels`, a firmware-listed channel whose **registration-time** `orig_flags` contains `IEEE80211_CHAN_DISABLED` is not considered eligible. The code must not modify `orig_flags` or clear `IEEE80211_CHAN_NO_IR`, `IEEE80211_CHAN_RADAR` or any other cfg80211 restriction.
- Native `BCME_UNSUPPORTED=-23` from `per_chan_info` continues to mark optional metadata unavailable; unknown 5GHz restrictions retain the conservative `IEEE80211_CHAN_NO_IR` flag. **Other firmware or transport errors now abort the legacy channel reconstruction** instead of being silently treated as a harmless unsupported feature. This prevents continuing interpretation with unverified per-channel status but is **not transactional** if previous channels were modified before the failure.
- The r4 native-error provenance fix remains; `fwil.c/h` shared per-call APIs do not toggle global interface error-mode state. Non-BCM4329 modern `chanspecs` path unchanged.
- WIFI-02, WIFI-03, WIFI-04 remain source-equivalent: independently compared using Git **stable patch IDs**, exact identical values: WIFI-02 `f3640d66bb029408fd9bbd66d24b52873696b8e4`; WIFI-03 `8c968d701aa204f86d0c62655a2e134092aeea10`; WIFI-04 `a265bc9566a6f8fba96af95434d377c7863d0efc`. Their `From` and `index` metadata differ because WIFI-01 was amended. The unrelated BigPart patch remains outside the four-member Wi-Fi series.
- Analogous [vendor Broadcom `bcmdhd` implementation](https://android.googlesource.com/kernel/msm/+/android-wear-5.1.1_r0.10/drivers/net/wireless/bcmdhd/wl_cfg80211.c) recognizes unsupported metadata but **does not supply proof that the MZ600's legacy 5GHz regulatory information is permissive**.
