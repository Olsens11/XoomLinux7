## Where the remaining gap actually lies

| Condition | Observed source behavior | Safety/compatibility consequence |
|---|---|---|
| Known valid `GET_VALID_CHANNELS` | Legacy helper stages and atomically ORs firmware restrictions | Correct bounded source behavior; subject to real firmware validation |
| Firmware query fails with native `NOTUP` or bus transport failure | The helper **returns without modifying flags** | Avoids corrupting channel arrays, but any **earlier cfg80211 recalculation is not rolled back** |
| `country` GET fails | Notifier returns before attempting any legacy refresh | Another early-return pathway requiring a defensible recovery policy |
| Country mapping absent, already set, or SET rejected | r7 attempts legacy-only current firmware requery | Directly analogous to vendor refresh method, but does not guarantee it succeeds |
| Current firmware channel requery also fails | Error logged by `void` notifier; channel view may stay as recalculated by cfg80211 | **Exact remaining gap:** stale or incomplete firmware restrictions in host presentation, despite firmware independently maintaining its own restrictions |
| `per_chan_info` unsupported | Current unknown-metadata 5GHz NO_IR stays conservative | Does not prove all regulatory DFS/power rules; cannot use `GET_CHANNELS_IN_COUNTRY` channel inventory as radar/passive metadata |

The firmware enforcing its own region is a plausible **additional hardware safety backstop** supported by Broadcom maintainer statements, but has not been proved specifically for the exact Motorola OEM2012 firmware under a failed country update. The driver must not *claim* accurate firmware/regulatory synchronization simply because firmware usually enforces legality.

## Additional pinned source audit: cfg lifetime, locking and WIFI-04 readiness

These findings were verified **after** the 19 exact-C tests and further narrow what a genuine recovery hook can safely reuse:

- In pinned `brcmfmac/core.c:brcmf_bus_started()`, `brcmf_cfg80211_attach()` allocates a new `cfg` after the bus moves to `BRCMF_BUS_UP`; in teardown `brcmf_cfg80211_detach()` frees that state. Thus a cache in `cfg` is naturally scoped to a **normal bus attach/detach lifecycle**, but an in-place firmware reset/recovery that does not recreate `cfg` has not been excluded. A generation-valid cache must never assume *all* firmware resets recreate the object.
- In pinned r7 `cfg80211.c:brcmf_bcm4329_prepare_escan()` (WIFI-04), the readiness check **only runs synchronously at scan entry**: `BRCMF_C_GET_UP`, optionally **sets `BRCMF_C_UP=1`**, then rereads `GET_UP`. This is an active scan-preparation transition, **not a passive firmware-UP event notifier**. It cannot safely be invoked from `reg_notifier` or used as an asynchronous readiness signal without a new lock/state/power sequencing analysis.
- In pinned `net/wireless/reg.c:update_all_wiphy_regulatory()`, `ASSERT_RTNL()` precedes the loop calling `wiphy_update_regulatory()`; `reg_call_notifier()` directly invokes the driver callback. This grounds regulatory-update serialization under **RTNL for this path**, but does **not prove** that other scan/init pathways changing or reading per-channel data take the same lock. The `cfg->usr_sync` mutex protects `brcmf_cfg80211_up/down` and has not been proven safe to nest inside the regulatory notifier.
- Therefore **do not implement a recovery worker or use WIFI-04 scan readiness as an event** yet. First identify a truly existing firmware-ready lifecycle callback/worker compatible with RTNL and `cfg` teardown, or keep all recovery synchronous and explicitly bounded at an appropriate existing operation boundary. Neither option is yet selected or implemented.

## Candidate recovery strategies and decision

1. **Unconditionally disable all channels on a query failure:** definitely conservative for subsequent host permission but can immediately disrupt an otherwise healthy 2.4GHz STA due to a transient `NOTUP`/transport error; not accepted as default.
2. **Unconditionally replay previous firmware list:** retains prior 2.4GHz connectivity but can be stale after a *real* country transition, new firmware generation, or failed SET that nonetheless modified firmware state; not a proven safety invariant.
3. **Add blanket `NO_IR` on all channels on failure:** avoids active probes but may change client connection behavior and is not equivalent to completely disabling RF, nor to restoring the firmware's actual permissions. Not accepted without a bounded, reversible retry design.
4. **Promote the firmware to regulatory authority by setting `REGULATORY_WIPHY_SELF_MANAGED` or rewiring Linux's global regulatory domain:** far broader than WIFI-01, ignores existing cfg80211 contract, and has no reason from this evidence.
5. **Preferred design for further qualification:** maintain a **last successfully validated firmware-current channel *restriction* snapshot**, associated with verified firmware country tuple/revision, device generation and successful query provenance; on later errors, distinguish firmware/bus `NOTUP` from alive-but-error states, and only reapply a snapshot when its provenance still matches. For an unknown/mismatched country or missing first snapshot, select and verify a conservative stop policy for new radio operations without guessing permissions, and requery after a proven firmware-ready event. Never widen cfg80211 rules, never infer `RADAR`/DFS from a list, and never permanently put a current-country valid list into `orig_flags`. **This is a candidate interface/state-machine design, not yet implemented or proven safe.** It must also specify locking, country SET partial-failure semantics and a no-silent-failure observable status.

### Specific next test gates before an r8 amendment

- Prove exact pinboard `reg_notifier` invocation/locking context and existing WIFI-04 firmware-UP event, so firmware retry is event-driven, bounded and cannot race or deadlock scan/connect.
- Prove a hardware/firmware-generation and country-tuple identity check is sufficient for caching validated channel restrictions; test country SET error with same vs changed firmware readback, requery error, malformed/empty list, bus-down and driver detach.
- Define the **initial no-snapshot** case with an explicit safe fallback; do not silently disable 2.4GHz if a bounded safe alternative is available, nor assume old 5GHz can initiate radiation.
- Once a narrowly justified design exists, **amend existing WIFI-01** (no extraneous fifth patch), preserve r7 source and full ABI hash; create an **exact r7→r8 change/rollback ledger on issue #4 immediately**, then run source-extracted C fault tests, static suites, original-nine full ARM build/259 ABI parity; eventually require separately authorized RAM-only OEM firmware physical validation and independent rollback.
