# Motorola Xoom Linux 7 — canonical *working* kernel patch series

**State:** source-level integration candidate; **NOT submission-ready** and **NOT submitted**. This directory is the **single authoritative patch-series location** for the current Xoom Linux 7 kernel work. The older `patches/lab/`, `patches/experiments/`, and `patches/upstream/rfc/` material is historical evidence or earlier RFCs, **not prerequisite patches**. Do not apply those ahead of this series. Each line in [`series`](series) is a single, self-contained logical change and applies after only the preceding entries in this file. **None depends on experimental Vxx patches.**

**Upstream source baseline:** `xoom-linux/linux@2404d27378503b4df74ab2cb0a8b7cd6cf9d5fc3` (developmental Linux 7). The generated `candidate-manifest.json` locks SHA256 of all four patch files. The entire series has passed **sequential `git apply --check` and byte-for-byte replay** against an unmodified, pinned upstream baseline in isolated scratch files. This is **source-application validation**, not a fresh full kernel build, a boot of the canonical series, or an upstream acceptance test. Do not describe it as such.

## Wi-Fi patch: established vs unresolved

**Physically supported by existing lab evidence:** BCM4329 firmware sends real Event 69 `SUCCESS` promptly, even when an event's decoded `bsscfgidx` cannot resolve. The owner-routing lab correction delivered that **real** terminal to the existing Linux `cfg80211_scan_done(aborted=0)` path; no synthetic completion. The firmware echoed chosen ESCAN `sync_id` values `0x1234`, `0x1235` and `0x1236` in independent tests; Linux's first in-session generated `0x1235` was also verified. Removing hardcoded ch36/no-SSID/forced-passive/500ms test policy enabled ordinary multichannel discovery on V28.

**Still open; must not misrepresent as solved:** (1) reliable *second* ESCAN in the same loaded device — existing evidence isolates `-52`, with a separate vendor-error diagnostic of `BCME_NOTUP=-4`; why the firmware is not UP/ready after successful completion is unproven; (2) scan generation/late-event/cancel/timeout/duplicate and interface lifetime synchronization, including 16-bit ID wrapping; (3) other firmware revisions and multi-interface/P2P, Bluetooth coexistence, other Xoom variants; (4) radio capabilities and effective regulatory flags from cfg80211/regdb, channel/DFS rules, power limits, association/authentication/DHCP; (5) simplification: the candidate currently contains **lab-era event instrumentation and test parameters**, excessive log messages and kernel style/checkpatch findings. Strip these by refactoring **this same patch**, not by creating a stacked cleanup patch, before upstream submission.

**Regulatory policy:** do not force `NO_IR` across all supported channels or clear regulatory flags to authorize transmission. Respect the effective cfg80211/regdb policy. Firmware-supported channel enumeration is not itself authorization to transmit on each channel. V29's intended source change preserves existing regulatory channel flags and only narrows unknown bandwidth; it is still awaiting physical testing.

**Submission gates** (all must pass before this is described as ready): reapply from pinned clean base after each revision, build full matched ARM kernel, modules and DTB, checkpatch/style and binding validation, verify actual hardware boot/USB/BigPart and independent rollback, two+ normal scans and ordinary network connection in legally permitted state, stale/abort/race tests, other-device regressions, consented real DCO signoff, and owner authorization for upstream submission. No private firmware/calibration, SSIDs, BSSIDs, access passwords or personal identity data belongs in these patches.

## Non-kernel components that this series cannot substitute for

The current runtime also relies on Debian armhf root filesystem on BigPart p8, a boot image/config and command-line, firmware blobs/NVRAM specific to a device, Bluetooth HCD/userspace, and system services. These **are not Linux source patches** and must be captured as separate reproducible deployment artifacts/manifests. This kernel series captures the actual *source-level* changes, not a flashable ROM or complete OS install.

## Reproducible update procedure

Source assembler: [`tools/forensics/assemble_mz600_canonical_kernel_series.py`](../../../tools/forensics/assemble_mz600_canonical_kernel_series.py). It reconstructs all four diffs from a hash-pinned untouched upstream source and known local experimental-source inputs, verifies each `git apply --check` sequentially in scratch storage and emits `candidate-manifest.json`. It refuses accidental overwrite; `--refresh` is explicit and verifies the previous stored patch SHA256 manifest before replacing files. **The assembler is developmental provenance only**—the four output patches apply directly to the upstream kernel without running experimental builders or intermediate patch versions.

The current compiler/test lineage is documented in [V21→upstream design](../../../docs/research/MZ600_V21_TO_UPSTREAM_EVENT69_COMPLETION_MODEL_2026-10-27.md), [V26b regulatory transition](../../../docs/checkpoints/MZ600_V26B_NO_IR_GATE_REMOVED_SECOND_ESCAN_FW_ERROR_2026-10-27.md), and [V28 first native scan](../../../docs/checkpoints/MZ600_V28_NATIVE_CFG80211_SCAN_AFTER_LAB_GATES_REMOVED_2026-10-27.md). Maintain ongoing, full details in those development records; keep the eventual kernel patch diff and commit message focused on *what is needed and why*, not chronology.
