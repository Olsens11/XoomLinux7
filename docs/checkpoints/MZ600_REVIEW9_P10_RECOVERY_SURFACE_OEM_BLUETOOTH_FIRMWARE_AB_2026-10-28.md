## Private firmware A/B and physical observations
1. **Generic BCM4329B1 HCD (A):** 17,332 bytes, SHA-256 `7fbab01012c909b9b2de0fda3a76c43fa1c5c150e08642d7d1dbaf4d5ebf887c`. Independently pinned on Desktop and Surface; transmitted using chunked COM9 to `/lib/firmware/brcm/BCM4329B1.hcd` on p10; on-device independent SHA PASS. HCI-only shutdown, `modprobe -r hci_uart`, `modprobe hci_uart` actually reloads the patch, dmesg: `Bluetooth: hci0: BCM4329B1 'brcm/BCM4329B1.hcd' Patch`. `hci0` reappears after an asynchronous initialization interval and **powers on** via `btmgmt` once present. The immediate `Invalid Index` after module insertion was a premature command during this interval, not lasting HCI absence. Subsequent BR/EDR-only `btmgmt ... find -b` began inquiry but **did not discover** Surface; Windows reverse inquiry likewise did not find the replacement Xoom. The first uninformed mixed BR/EDR+LE inquiry was an invalid test for this non-LE controller; BR/EDR-only invocation is required.
2. **Exact Motorola OEM MZ600 HCD (B):** Both private OEM HRI39 and HRI66 images give **17,770 bytes**, SHA-256 `2d68db625a3e4e32fcc30813746fb84ca37491e055ad5e5e5d43057e4f2c16ea`. Different bytes and size from generic A. Independently transferred Pi→Surface with restricted, one-shot LAN sender (then server CLOSED), verified on Surface; chunked COM9 staged on p10 at higher-priority device-specific lookup filename `/lib/firmware/brcm/BCM4329B1.motorola,stingray.hcd`, full on-Xoom SHA PASS. When `hci_uart` reloaded, kernel **selected Motorola B**: `Bluetooth: hci0: BCM4329B1 'brcm/BCM4329B1.motorola,stingray.hcd' Patch`; then **`BCM: failed to write clock (-110)`**, **`BCM: Reset failed (-110)`**. This is a **real HCI initialization timeout**, not proof of RF discovery or pairing. BlueZ service itself remained active but controller index temporarily absent. Wi-Fi stayed connected.
3. **Safe restoration:** preserved Motorola B bytes unchanged but moved device-specific active filename to `/lib/firmware/brcm/BCM4329B1.motorola,stingray.hcd.trial-20261028` (full SHA reverified, no more priority match). Generic A `BCM4329B1.hcd` left unchanged. Quiesced BlueZ and HCI; `modprobe -r hci_uart` exit0; `modprobe hci_uart` exit0; dmesg newly confirms **generic A patch again**, HCI registration waited for actual `Index list with 1 item`, `btmgmt power on` returned `hci0 Set Powered complete` and `current settings: powered ssp br/edr`. `wlan0` stayed `GENERAL.STATE:100 (connected)`; COM9 unaffected. Both original private files remain available for offline comparison. **This is the end-of-test live state**, not earlier report's powered-OFF state.
4. No pairing, trusting, connecting, HID events, numeric confirmation or authenticated Bluetooth data transfer established on replacement Xoom. The original Recovery project's saved Windows device entry is **not** evidence of a connection to replacement Linux 7 Xoom. Bluetooth was powered for controlled testing, but simultaneous real Wi-Fi+BT traffic has not been validated.

## Kernel source analysis (source-backed; not an accepted fix yet)
- Actual current clean nine-review Stingray diagnostic DTS: `arch/arm/boot/dts/nvidia/tegra20-motorola-stingray-clean-usb.dts` (isolated build source); upstream board DTS `tegra20-motorola-wingray.dts` same node. `serial@70006200/bluetooth` has `compatible = "brcm,bcm4329-bt"`, `max-speed = <3375000>`, `clock-names = "txco"`, I7 shutdown GPIO and U0 reset GPIO; Tegra UART `nvidia,adjust-baud-rates` range includes 1M–4M.
- `drivers/bluetooth/hci_bcm.c` `bcm_set_baudrate()` executes vendor `0xfc45` **48MHz controller clock write when requested speed >3000000 and !no_uart_clock_set**. Generic BCM4329 device-table entry has **no per-device override**; other chips (e.g. CYW4373A0) carry `no_uart_clock_set=true` for chip-specific reasons. The OEM B failure at the clock write matches this path, but **does not yet prove** clock write unsupported versus firmware incompatibility, UART signal, clock, HCI flow control, or power/reset state.
- Tegra20 `drivers/tty/serial/serial-tegra.c` has `support_clk_src_div=false`; `tegra_set_baudrate` computes `DIV_ROUND_CLOSEST(clk_get_rate(uart_clk), baud *16)`. With **216MHz assumed actual clock**, 3375000 yields divisor4 exactly, while requested 3000000 rounds to divisor5 yielding ~2700000 actual. Verify the runtime UART clock rate before treating 216MHz as measured. **Never claim one-line max-speed=3000000 necessarily reproduces Motorola 3Mbps**.
- Source-only next experiments must keep **exactly one logical issue per patch**. First determine whether a BCM4329-specific suppression of `0xfc45` is justified and test with unchanged 3.375Mbps host (could still fail downstream); a *separate* UART clock/divisor analysis is needed to reproduce true 3Mbps if required. Do not indiscriminately use `no_uart_clock_set` for other Broadcom chips, alter shared U4/I7 power votes, change firmware/DT in the same run, or present a guessed upstream solution.
